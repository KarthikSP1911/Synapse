# Mathz

Mathz is an adaptive mental-maths trainer. It drills four skills — **multiplication, percentages, fractions and squares** — in short sessions, records your accuracy and speed for every individual question, and steers practice toward what you find hardest and what is due for review.

## Features

- **Four skills**, each with its own setup, statistics and progress view: multiplication (1–20 tables), percentages, fractions and squares.
- **Session types** for every skill: fixed length (10, 20, 30, 50 or 100 questions), endless, and timed (30, 60 or 120 seconds). Timed sessions track a personal best per skill and length.
- **Focus**: an adaptive mix (default), only your weak questions, or only questions due for review.
- **Adaptive selection**: about 30% of questions (configurable) come from your weakest questions, weighted by weakness; due reviews are favoured next; recently asked and already-seen questions are avoided where alternatives exist. Unseen variations of a weak *concept* (for example another 25% question when 25% is your weak spot) are boosted too.
- **Spaced repetition**: one Leitner implementation shared by every skill (boxes 1–5, reviewed after 1, 2, 4, 8 and 16 days). Only unassisted correct answers advance a box; wrong, skipped, timed-out and hinted answers do not.
- **Hints, skip, pause/resume and an optional per-question time limit.** A correct answer after a hint counts as correct but does not advance the box. Pausing stops a timed session's clock.
- **Mistake review**: retry the misses of one session, or of the last 7 days, filtered by skill and exercise type. Original attempt history is never modified.
- **Worked explanations** after a miss, generated by deterministic rules (no AI service involved).
- **Progress dashboard** with a skill filter: accuracy and speed per skill and per exercise type, weak and mastered questions, weakest concepts, upcoming reviews, Leitner box counts, a trend chart, and (for squares) recall by number range.
- **Tables page**: the 20×20 multiplication heatmap, plus a separate 1–100 squares heatmap. Skills are never merged into one misleading heatmap.
- **Accounts**: sign up and log in with email and password. Every account has its own statistics, history and streak; "Remember me" keeps you signed in for 12 months. Practice requires an account. The first account to sign up inherits any data recorded before accounts existed.
- **Profile** (the user icon in the header): a year-long practice calendar heatmap (one square per day, darker for busier days), current and longest streak, active days, and a per-skill summary. Days follow the time zone your browser reports at login.
- **Settings** (stored in this browser): weak-question share, recent-question window, default difficulty, enabled exercise types per skill, default session length, per-question time limit, explanations, hints and live stats.
- **Installable app (PWA)**: a web app manifest, generated icons (including a maskable one) and a service worker. On phones and tablets a non-intrusive "Install Mathz" banner appears when installation is supported (the native prompt on Chromium, Share-sheet steps on iOS Safari); it stays away once installed, running as an app, or dismissed. The service worker is registered in production builds only.
- **Offline and slow networks**: after one online visit the app opens and practice runs with no connection. Practice always runs in the browser (`src/features/offline/lib/guest/api.ts`), so answers never wait on the network. Signed-in users' sessions are saved on the device and uploaded in the background (`src/features/offline/lib/sync/`, `POST /api/sync`) when the network is back; the server re-checks every answer and ignores repeats, so a retry can never double-count. Screens are served network-first with a 4 s cut-off, then from the last stored copy (`public/sw.js`). First sign-in, sign-up and "Try without an account" still need a connection once. Run `npm run db:migrate` to add the `client_id` column the upload uses.
- **Coins, Streak Shields and paid hints**: practice and games pay coins, coins buy Streak Shields that protect the streak on a missed day, and every hint costs coins and starts a short cooldown. The wallet is in the header and the shop is at `/rewards`. See [Coins, shields and hints](#coins-streak-shields-and-hints).
- **Patches** (`/games/patches`): a spatial logic puzzle. Divide the grid into connected patches that each hold one clue and match it: a number is the patch's area, a symbol its shape (square, wide, tall or freeform), a plain dot says nothing (any rectangle). Every puzzle is generated on demand from a valid partition and proved to have exactly one solution. See [Patches](#patches).
- **Keyboard-first** practice with visible focus rings, light/dark themes, and respect for `prefers-reduced-motion`.

## Skills and exercises

| Skill | Exercise types |
| --- | --- |
| Multiplication | `a × b` for any left and right numbers from 1 to 20 |
| Percentages | percent of a number · what percentage · increase / decrease (including "price rises from 80 to 100" and multi-step changes) · conversions between percentages, decimals and fractions |
| Fractions | simplify · fraction of a number · compare (which is larger, or greater / less / equal) · conversions between fractions, decimals and percentages |
| Squares | `n²` · `√n²` · missing value (`14 × 14 = ?`, `?² = 441`), with ranges 1–20, 1–50, 1–100 or any custom range within 1–100 |

Percentage and fraction practice have three **difficulty levels**:

- **Percentages** — *Beginner*: 1, 5, 10, 20, 25, 50, 75%. *Intermediate*: other whole-number percentages and bigger numbers. *Advanced*: decimal percentages (12.5%), percentages over 100 and multi-step changes. The range of numbers you take a percentage of is configurable (1–10,000).
- **Fractions** — difficulty controls numerator and denominator size and how tricky the simplifying is. Beginner "fraction of" questions always have whole-number results; advanced ones may need decimals. Conversions only use fractions with terminating decimals, because answers are checked exactly (see below).

## Getting started

### Prerequisites

- Node.js 20 or newer
- A Postgres database (a free Neon project works well)

### Setup

```bash
# 1. Install dependencies
npm install

# 2. Configure the database connection
cp .env.example .env.local     # then set DATABASE_URL

# 3. Create / upgrade the tables
npm run db:migrate             # existing databases: upgrades in place, keeps all data (adds accounts)
#    (a brand-new database can use `npm run db:push` instead)

# 4. Start the dev server
npm run dev
```

Open <http://localhost:3000>.

## Coins, Streak Shields and paid hints

Every amount below lives in one file, `src/features/rewards/lib/economy.ts` (`ECONOMY`). Change a value there and the games, the shop, the server and the tests follow.

| Activity | Coins |
| --- | --- |
| Correct practice answer | 2 |
| Practice session finished (at least 5 answered, at least 50% right) | 5 bonus |
| Correct MindSprint round / perfectly recalled Number Recall round | 2 each |
| MindSprint / Number Recall session finished (at least 3 rounds, at least 50% right) | 5 bonus |
| Solved Sudoku, Queens, Zip or Patches: Easy / Medium / Hard / Expert | 10 / 15 / 20 / 30 |
| 2048 run, once, by highest tile: 128 / 256 / 512 / 1024 / 2048 / 4096 / 8192 / 16384+ | 3 / 5 / 8 / 12 / 20 / 30 / 40 / 50 |
| **Spend**: Streak Shield (up to 5 held) | 100 |
| **Spend**: a hint that is actually delivered (then 5 s cooldown per game or session) | 5 |

- **What earns nothing**: opening a page, starting a game, refreshing, wrong/skipped/timed-out answers, a revealed Sudoku, an abandoned puzzle or session, a 2048 game left after a few moves, the same answer submitted twice within 400 ms. Each reward has an idempotency key made from the thing it pays for (`practice:<session>:<answer time>`, `queens:<game id>`, ...), so a retry, re-render, re-upload or sync pays once.
- **Streak Shields** protect one missed calendar day each (the user's own time zone). The next time the app opens or syncs, a missed day with a shield available is covered automatically. A gap is covered whole or not at all (shields are not wasted on a streak that breaks anyway); a shield only covers days on or after the day it was bought, so it cannot revive a streak that already broke; one shield per day, never twice for the same date. A protected day keeps the streak alive but is **not** activity: it adds nothing to streak length or active days, earns no coins, and does not appear on the calendar.
- **Hints** (Queens, Zip, Patches, Sudoku and practice) share one mechanism (`use-paid-hint.ts` over `requestHint` in `service.ts`). The hint is worked out first; if there is none to give, nothing is charged. Then the wallet checks the cooldown and balance and takes the price in one saved step, and only if that succeeded is the hint shown. The cooldown is stored in the wallet (not in React state), so rapid clicks, the `H` key, touch events and reloads cannot skip it.
- **Where the money is**: a guest's wallet lives in this browser only and is not carried to a new account (the same rule as their practice history). A signed-in user's wallet is kept on the server (`wallets`, `wallet_transactions`) and cached on the device so the app still works offline. Earnings are credited by the upload routes from records the server has just re-validated (never from an amount the device sends); hint charges the device made offline are re-charged by the server at its own price when it syncs; shield purchases go to the server and need a connection.
- **Deploying**: run `npm run db:migrate` (adds `0009_wallet.sql`, additive and idempotent) **before** deploying this code. Until it has run, uploads that earn coins fail with a 500 and the device keeps retrying, so nothing is lost, but nothing syncs.

## Upgrading an existing database

`npm run db:migrate` applies `src/db/migrations/0001_multi_skill.sql` in a single transaction. It is **additive and idempotent**:

- adds skill, focus, configuration, pause and per-question-limit columns to `practice_sessions`;
- adds skill, exercise type, stable question id, difficulty, prompt, answer text, outcome and hint columns to `question_attempts`, back-filled for every existing attempt (they were all multiplication), and makes the four multiplication-specific columns nullable (they stay filled for multiplication);
- creates `question_stats` and copies every row of `pair_statistics` into it (accuracy, streaks, weakness, Leitner box and due date), so multiplication history carries over;
- adds indexes. Nothing is dropped or rewritten, and running it again changes nothing.

`pair_statistics` is **no longer written** after the migration; it is kept so no data is lost and can be dropped later. `table_statistics` is still maintained for multiplication. Run the migration **before** starting the new code: the old code cannot insert attempts once the new NOT NULL columns exist, so any other deployment sharing the database needs to be redeployed at the same time.

### Patches

Standalone game at `/games/patches`, built on the shared puzzle shell like Queens and Zip (Easy to Expert, a larger board per level in the setup, resume, stats, coins, paid hints, streak). Run `npm run db:migrate` to add `patches_sessions` (migration `0010`).

- **Rules**: every cell is in exactly one patch, every patch is connected (edges, not corners) and holds exactly one clue. A clue may give an area, a shape, both, or nothing. Square, wide and tall mean a rectangle; the freeform symbol (always with an area) allows any connected shape; a clue with neither is any rectangle.
- **Playing**: drag from one corner of a patch to the opposite one (touch, mouse or pen); on a freeform clue, drag across the cells it should take. Nothing is placed until you let go, and a patch that breaks a rule is refused with the reason and leaves the board as it was. Every clue has its own colour (its symbol, and the fill of its patch), and the preview fills in that colour as you drag. Nothing needs a Remove button: drag from the edge of a patch to pick it up and resize it, draw over a patch to replace it, or tap a patch to erase it (Undo takes any of it back). Undo, Redo, Reset, Restart, Check and Hint are on the play screen; Auto-check marks a clue or cell that no patch can serve any more. Arrow keys, Enter (starts, places, or erases the patch under the cursor), Esc and Delete work without a pointer.
- **Hints** point at a clue that is easy to place (or at a wrong patch, with the reason), and a second press on the same clue shows its patch. A hint never places anything. Price, cooldown and order are the shared ones above.
- **Code**: `src/features/games/patches/lib` is pure TypeScript (format, shape rules, solver, generator, rules, drawing state, game, hints, storage), `components` is the board and play screen. Details are in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md#patches).

### MindSprint (flash arithmetic)

`/games/mindsprint` is a game rather than a drill: numbers flash one at a time, and the player gives the result after the last one disappears. Logic is in `src/features/games/mindsprint/lib/`, UI in `src/features/games/mindsprint/components/`.

- **Sequential evaluation**: operators apply left to right to the running total (`20 × 3 − 5 = 55`, `10 + 5 × 2 = 30`).
- **Exact**: all arithmetic uses the rationals in `src/lib/rational.ts`. Every number, running total and answer is a finite decimal with at most the round's decimal places; divisions are always exact and never by zero. Answers are compared exactly (`3.50` equals `3.5`).
- **Digits** means digits in the whole part (`1` = 1-9, `2` = 10-99 ...). With negatives off, no number, total or answer is below zero.
- **Scoring**: a correct round earns `100 × difficulty multiplier` points (digits, length, operations, decimals, negatives and speed raise it); anything else earns 0.
- **Persistence**: finished sessions are saved on the device under the viewer's storage key (`...:mindsprint`) and, for accounts, uploaded to `POST /api/sync/mindsprint` (table `mindsprint_sessions`, migration `0004_mindsprint.sql`). The server re-checks every sequence and recomputes the score.

Run `npm run db:migrate` to create the table before signed-in users play MindSprint.

## How it works

1. **Setup**: the home page shows the four skills with your progress. Choosing a skill shows only that skill's options. Starting creates a session (`POST /api/sessions`) storing the validated configuration.
2. **Pools**: a configuration defines a finite, deterministic **pool** of questions (`src/features/skills/lib/pools.ts`), filtered by difficulty tier and range, with every question parsed back through the id parser so it has an exact, sensible answer. Because pools are finite, the same question comes round again and its history accumulates.
3. **Ask**: `GET /api/sessions/:id/next` loads that skill's statistics and `selectNext` (`src/features/skills/lib/practice/selection.ts`) picks a question. The response contains the prompt and answer format, never the answer.
4. **Answer**: `POST /api/sessions/:id/attempt` sends the question id and the raw answer. The server **rebuilds the question from its id**, checks it belongs to the session, validates the answer, and records the attempt, the session totals, the question's statistics and its Leitner box.
5. **Review and report**: the summary, progress and tables pages read the stored data.

### Question ids and concepts

Every question has a stable id built from its operands, so the server can rebuild it and history attaches to it:

```
multiplication:12:8        percentage:of:25:80          percentage:what:15:60
percentage:change:increase:200:15   percentage:change:find:80:100   percentage:change:multi:200:10:-10
percentage:convert:d2p:0.75         fraction:simplify:12:16         fraction:of:3/4:80
fraction:compare:larger:3/4:2/3     fraction:convert:f2d:1/4        square:value:17   square:root:289
```

Related questions share a **concept** (`square:17` covers `17²`, `√289` and the missing-value forms; `percentage:pct:25` covers every 25% question; a fraction concept covers its simplify / of / convert forms). Concepts drive the "weakest concepts" view and the boost for unseen variations.

### Code layout

Code is grouped by feature (`src/features/<feature>/{components,lib,server}`), with shared UI in `src/components`
and shared logic in `src/lib`. The practice core is `src/features/skills/lib/`: types, question ids, generators and
explanations (`build.ts`), pools and answer validation, all database-free. Database access lives in each feature's
`server/` folder, pages and API routes in `src/app/`, and the schema and migrations in `src/db/`.

See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) for the full folder tree, conventions and the reasoning behind them.

### Answer validation

Done on the server (and mirrored on the client only to disable *Submit* for malformed input). Numbers are compared as **exact rationals**, never floats, with no tolerance: `0.5`, `0.50` and `.5` are equal, `0.49` is not. A `%` is accepted only where the answer is a percentage. Fractions are `a/b` with optional spaces around the slash; equivalent fractions are accepted unless the exercise needs lowest terms (simplify, "convert to a simplified fraction"). Text that merely looks similar (`3/40` for `3/4`) is never matched by string comparison. Malformed input is rejected (HTTP 400) rather than marked wrong.

### Weakness score

Per question: starts from the error rate (`100 − accuracy`), adds 10 if the average response is slower than the skill's threshold (5 s for multiplication, 8 s squares, 10 s percentages, 12 s fractions), 10 per consecutive miss after the first, and 10 after a hinted answer; subtracts 20 after four unassisted correct answers in a row; clamped to 0–100. The multiplication formula is unchanged from earlier versions.

### Compression

- **Practice kept on the device** (`mathz:guest:v1`, `mathz:user:v1:<id>`): a prompt, skill, exercise type, difficulty and correct answer repeat on every attempt and statistics row, yet all follow from the question id. `src/features/offline/lib/guest/pack.ts` leaves them out (keeping a record whole whenever the rebuilt text would differ), then `src/features/offline/lib/compression.ts` compresses each part with lz-string. Each session and each slice of the statistics is its own part, so saving after an answer only recompresses what changed. Data saved before this existed is still read and is converted on the next save.
  Measured on simulated play across all four skills (characters stored, including the cost of splitting into parts):

  | History | Plain JSON | Stored now | Reduction | Load + save |
  | ------- | ---------- | ---------- | --------- | ----------- |
  | 480 attempts | 320,636 | 12,945 | **24.8x** | about 5 ms |
  | 6,000 attempts (40 sessions) | 2,094,254 | 62,296 | **33.6x** | about 21 ms |

  localStorage counts two bytes per character, so the larger history went from about 4 MB, close to the usual 5 MB quota, to about 120 KB.
- **Uploading offline practice** (`POST /api/sync`): the browser gzips bodies over 1 KB (`Content-Encoding: gzip`) and falls back to plain JSON if the server refuses. The server accepts both and caps the decompressed size (`src/features/offline/lib/sync/body.ts`).
- **Pages, scripts and API responses** are gzipped by `next start` (Vercel does the same, with brotli), so they are not compressed again in code.
- **Not compressed on purpose:** the database (Postgres already compresses large values, and these columns are short), React state, and small `localStorage` values such as settings, where the result would be larger than the input.

### API

| Method | Endpoint                    | Purpose                                                              |
| ------ | --------------------------- | -------------------------------------------------------------------- |
| POST   | `/api/sessions`             | Create a session (`fixed`, `endless`, `timed` or `review`)           |
| GET    | `/api/sessions/:id/next`    | Next question (`?exclude=<id>`), or `{ "finished": true }`           |
| POST   | `/api/sessions/:id/attempt` | `{ questionId, userAnswer, responseTimeMs, hinted?, outcome? }`      |
| POST   | `/api/sessions/:id/pause`   | Stop the session clock                                               |
| POST   | `/api/sessions/:id/resume`  | Restart it; paused time pushes a timed deadline back                 |
| POST   | `/api/sessions/:id/end`     | Mark a session as ended                                              |

`outcome` is `answered` (default), `skipped` or `timed_out`; a timeout is only accepted if the session has a per-question limit that really elapsed. The original multiplication payloads (`selectedLeftNumbers` / `selectedRightNumbers` to create a session, `{ left, right, userAnswer }` for an attempt) are still accepted. Errors are `{ "error": "..." }` with status 400 (invalid input), 404, 409 (session completed or paused) or 500.

## Testing

`npm test` runs the unit tests with no external database. The wallet's SQL is tested against an in-process Postgres (PGlite, a dev dependency) with the real `0009_wallet.sql` applied, including concurrent purchases, duplicate keys and the CHECK constraints. The first group of tests (originally 83) covers: rational arithmetic, every spec example, question ids (round-trip and rejection of malformed ones), answer validation edge cases, difficulty-specific pool generation (every question in every pool is checked for tier, uniqueness and an exact answer), config and session-request validation, Leitner transitions and due dates, weakness scores, adaptive selection (rates, weighting, recent avoidance, fallbacks, focus modes), pause-aware timeouts, settings migration, and the square-range chart.

Not covered by automated tests: the SQL that updates session totals and the React components. During development these were exercised by hand against a development database (all four skills end to end: creating sessions, answering, skipping, hints, timeouts, pause/resume, mistake review, summary, progress and tables pages) and by `npm run build`, `npm run lint` and `npm run typecheck`; there is no committed end-to-end suite.

## Notes

- There is no authentication: statistics are shared by everyone using the same database.
- The app needs `DATABASE_URL` at runtime; pages that read statistics are rendered on demand, so builds do not need database access.
- Settings live in `localStorage`, so they are per browser.
